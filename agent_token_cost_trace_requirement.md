# Agent Token Accounting & Cost Trace – Implementation Requirement

## Purpose

Update the existing **AI Agent Trace / Observability** implementation so that token usage and cost are calculated correctly at the **LLM-call level** and rolled up accurately to the **agent level**.

The current trace UI shows values such as:

```text
run_agent [Snow_Inventory_Agent]      23,146 tokens
├─ prompt_build                        8,896 tokens
├─ tool_call [Server_CMDB_Info]             -
└─ llm_response                          615 tokens
```

The current **Token Breakdown** also shows a very large value under `User prompt`, even though the real user query is only a short sentence.

This indicates that the implementation is likely mixing:

- actual user-message tokens,
- complete LLM input tokens,
- prompt-build estimates,
- tool/context tokens,
- and output tokens.

The required implementation must separate these correctly.

---

# 1. Core Rule

Token accounting must be based on the **actual LLM API/model call**.

For every LLM invocation capture:

```text
input_tokens
output_tokens
total_tokens
cached_input_tokens      # if provider returns this
reasoning_tokens         # if provider returns this
```

The authoritative rule is:

```text
total_tokens = input_tokens + output_tokens
```

If the provider returns its own `total_tokens`, use the provider value and validate that it reconciles with the individual values where applicable.

Do **not** treat Python prompt-building work as a separate billable token event.

---

# 2. What Is an Input Token?

Input tokens are all tokens sent into the LLM for a specific model call.

This may include:

```text
System prompt
Developer/agent instructions
User prompt
Conversation history
Tool definitions / tool schemas
RAG context
Retrieved documents
Tool results
Previous agent output
Routing context
Other model context
```

Example:

```text
System prompt              1,500
Agent instructions         2,100
User prompt                   10
Conversation history         500
Tool definitions           3,200
RAG/context               15,221
--------------------------------
Total input tokens        22,531
```

The user prompt must represent only the actual user message.

For example:

```text
"Please provide installed servers type wise"
```

should be counted only as the token count of that message, not as the complete 22K-token model input.

---

# 3. What Is an Output Token?

Output tokens are tokens generated by the LLM.

They may include:

```text
Natural-language answer
JSON
Structured output
Tool-call name/arguments
Generated SQL
Generated code
Agent-to-agent message
Reasoning tokens if separately exposed by the provider
```

Example:

```text
Input tokens  = 22,531
Output tokens =    615
------------------------
Total tokens  = 23,146
```

This is a valid and reconcilable token total.

---

# 4. Tool Calls

A normal local/API tool execution is not itself an LLM call.

Example:

```text
tool_call [Server_CMDB_Info]
```

should normally report:

```text
llm_input_tokens  = 0
llm_output_tokens = 0
llm_total_tokens  = 0
```

However, the tool result may later become part of the **input of another LLM call**.

Example:

```text
User
  ↓
LLM decides to call Server_CMDB_Info
  ↓
Server_CMDB_Info executes
  ↓
Tool returns 500 rows
  ↓
Tool result is inserted into next model prompt
  ↓
Those tool-result tokens become INPUT TOKENS for that next LLM call
```

Do not assign those tokens directly to the tool execution itself.

---

# 5. Prompt Build Span

The existing trace contains:

```text
prompt_build       8,896 tokens
```

The prompt-build span can display an **estimated prompt size**, but it must not be treated as an additional billable LLM token count.

Recommended representation:

```text
prompt_build
    estimated_input_tokens: 8,896
    duration: 8 ms
```

Then the actual model call should contain the authoritative provider usage:

```text
llm_call [claude-opus-4.6]
    input_tokens: 22,531
    output_tokens: 615
    total_tokens: 23,146
```

Do not calculate:

```text
prompt_build tokens + llm tokens
```

because that can double-count the same prompt.

# 7. Parent Agent Roll-Up

The parent agent total must equal the sum of all real LLM calls belonging to that agent execution.

Example:

```text
LLM Call 1
input: 600
output: 30
total: 630

LLM Call 2
input: 800
output: 40
total: 840

LLM Call 3
input: 950
output: 100
total: 1,050
```

Agent totals:

```text
Input Tokens  = 600 + 800 + 950 = 2,350
Output Tokens = 30 + 40 + 100   =   170
Total Tokens  = 2,520
```

Do not add tool spans or prompt-build estimates again.

# 9. Cost Calculation

For every LLM call calculate:

```text
input_cost =
    non_cached_input_tokens
    × input_price_per_million
    / 1,000,000

cached_input_cost =
    cached_input_tokens
    × cached_input_price_per_million
    / 1,000,000

output_cost =
    output_tokens
    × output_price_per_million
    / 1,000,000
```

Then:

```text
llm_call_cost =
    input_cost
    + cached_input_cost
    + output_cost
```

Agent cost:

```text
agent_llm_cost = SUM(all LLM call costs)
```

If tools have external/API charges:

```text
agent_total_cost =
    agent_llm_cost
    + SUM(tool/API cost)
```

Do not invent tool cost where no cost exists.

# 10. Model Pricing Configuration

Do not hardcode pricing directly inside trace logic.

Use a central model pricing configuration.

Example:

```python
MODEL_PRICING = {
    "claude-opus-4.6": {
        "input_per_million": ...,
        "cached_input_per_million": ...,
        "output_per_million": ...
    },
    "another-model": {
        "input_per_million": ...,
        "cached_input_per_million": ...,
        "output_per_million": ...
    }
}
```

Pricing must be replaceable/configurable without modifying trace code.

If pricing is unavailable for a model:

```text
cost_status = "pricing_unavailable"
```

Do not silently calculate using the wrong model's price.

# 15. Token Optimization Metrics

The current UI has:

```text
Potential tokens
Actual tokens
Tokens avoided
Optimization rate
```

Keep these only if their meanings are clearly defined.

Recommended definitions:

```text
potential_tokens =
    estimated tokens that would have been sent without optimization

actual_tokens =
    actual provider-reported input tokens

tokens_avoided =
    max(potential_tokens - actual_tokens, 0)

optimization_rate =
    tokens_avoided / potential_tokens * 100
```

Do not set:

```text
potential_tokens = total input + output tokens
```

unless that is explicitly the intended definition.

Optimization should normally focus on **input/context reduction**, not generated output.

# 17. Important Validation Rules

Add validation to the backend.

### Rule 1

```python
if input_tokens is not None and output_tokens is not None:
    expected_total = input_tokens + output_tokens
```

Validate against provider total where appropriate.

### Rule 2

Agent total must equal the sum of child LLM call totals.

```python
agent_total_tokens =
    sum(span.total_tokens for span in llm_spans)
```

### Rule 3

Agent input total:

```python
agent_input_tokens =
    sum(span.input_tokens for span in llm_spans)
```

### Rule 4

Agent output total:

```python
agent_output_tokens =
    sum(span.output_tokens for span in llm_spans)
```

### Rule 5

Do not add:

```text
prompt_build estimated tokens
tool result estimated tokens
component-breakdown tokens
```

to the authoritative total again.

These are descriptive measurements of content that ultimately becomes part of an LLM call.
